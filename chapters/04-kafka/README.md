# 4장. Kafka 운영

## 이 장은 어디서 시작하나?

3장에서 결제 변경이 Kafka 토픽으로 흐르기 시작했습니다. 이제 정산, 실시간 집계, 레이크 적재가 모두 이 토픽을 읽습니다. 브로커 하나가 죽거나, 소비자가 재시작되거나, 판매자 한 명에게 주문이 몰리면 무슨 일이 생기는지 하나씩 확인합니다. Kafka 기초 개념은 이 장에서 실험과 함께 공부합니다.

환경: `docker compose --profile kafka up -d --wait`. KRaft 노드 3대(브로커와 컨트롤러 겸용), 기본 복제 3, `min.insync.replicas=2`, 파티션 3. 호스트 접속 주소는 `127.0.0.1:19092,127.0.0.1:29092,127.0.0.1:39092`입니다. CDC 토픽이 필요한 실험은 `--profile cdc`로 올립니다.

## 무엇을 공부하나?

- 로그, 세그먼트, 오프셋, 파티션, 키 해시, 컨슈머 그룹 (블로그 12편)
- 프로듀서 batch, linger, acks, idempotence (블로그 13편)
- 복제: 리더, 팔로워, ISR, high watermark, `min.insync.replicas`, unclean leader election
- 오프셋 커밋: 자동 커밋, 처리 전 커밋, 처리 후 커밋
- 리밸런스 프로토콜: eager, cooperative-sticky, static membership(`group.instance.id`), 새 컨슈머 프로토콜(KIP-848, `group.protocol=consumer`)
- lag을 건수와 시간으로 보기
- 보존(`retention.ms`), 컴팩션(`cleanup.policy=compact`), tombstone, `delete.retention.ms`
- 파티션 수와 키 분포
- 롤링 재시작, 운영 지표

## KRaft는 어떻게 생겼나?

실험 전에 `kafka-metadata-quorum.sh describe --status`와 `--replication`으로 컨트롤러 쿼럼을 봅니다. 노드 하나를 멈췄을 때 리더 컨트롤러가 바뀌는 시간과, 두 대를 멈췄을 때 메타데이터 변경(토픽 생성)이 막히는 것을 확인합니다. 결과는 이 절에 짧게 적습니다.

## 실험

### E4-1. acks=all이면 메시지를 잃지 않을까?

- 질문: 쓰는 도중 파티션 리더를 죽이면 확인 응답을 받은 메시지 중 사라지는 것이 있을까?
- 바꿀 조건: `acks` 1과 all, `min.insync.replicas` 1과 2.
- 방법: 일련번호를 붙인 메시지를 쓰고 확인 응답을 받은 번호를 기록, 리더 `kill -9`, 끝까지 읽어 빠진 번호를 셉니다.
- 볼 것: 확인받고 사라진 건수, 쓰기 오류 건수, 리더 전환 시간.
- 근거 등급: `E2`.

### E4-2. ISR 밖 복제본이 리더가 되면?

- 질문: `unclean.leader.election.enable=true`에서 뒤처진 복제본만 남았을 때 리더가 되면 무엇을 잃을까?
- 방법: 팔로워 하나를 멈춰 뒤처지게 한 뒤 나머지를 죽이고 그 팔로워만 살립니다.
- 볼 것: 사라진 오프셋 범위, 소비자가 보는 오프셋 되감김.
- 근거 등급: `E2`.

### E4-3. 처리하고 죽으면 몇 번 처리될까?

- 질문: 처리 전 커밋과 처리 후 커밋에서 소비자를 `kill -9`하면 중복과 유실은 각각 몇 건일까?
- 방법: 소비자가 처리 결과를 MySQL 표에 쓰고, 처리와 커밋 사이 여러 지점에서 죽입니다.
- 볼 것: 중복 처리 건수, 유실 건수, 멱등 키(`(표, 키, GTID)`)를 넣었을 때의 결과.
- 근거 등급: `E2`.

### E4-4. 리밸런스 동안 처리는 얼마나 멈출까?

- 질문: 소비자를 하나 넣거나 뺄 때 그룹 전체가 멈추는 시간은 프로토콜마다 얼마나 다를까?
- 바꿀 조건: eager(range), cooperative-sticky, static membership, 새 컨슈머 프로토콜.
- 볼 것: 파티션별 마지막 처리 시각의 공백, 리밸런스 횟수, 정지 시간 p50과 최댓값.
- 근거 등급: `E2`.

### E4-5. lag 10만 건은 몇 초 늦은 걸까?

- 질문: 같은 건수 lag이 유입률에 따라 얼마나 다른 시간 지연이 될까?
- 바꿀 조건: 부하 생성기 주문률 10, 100, 500/s.
- 볼 것: 건수 lag, 시간 lag(지금 시각 − 마지막 처리 레코드의 타임스탬프), 둘의 비율.
- 근거 등급: `E2`.

### E4-6. 지운 판매자가 컴팩션 뒤에 되살아날까?

- 질문: 판매자 상태를 담는 컴팩션 토픽에서 tombstone을 쓴 뒤 `delete.retention.ms`가 지나면, 늦게 처음부터 읽는 소비자는 그 판매자를 볼까?
- 볼 것: tombstone 전후와 보존 기간 뒤 재생 결과, 세그먼트가 닫혀야 컴팩션이 도는 조건.
- 7장 E7-5(삭제 되살아남)와 이어집니다.
- 근거 등급: `E2`.

### E4-7. 인기 판매자 하나가 파티션을 막으면?

- 질문: 키를 `seller_id`로 두고 주문 절반이 판매자 하나에 몰리면 파티션별 lag은 어떻게 갈릴까?
- 조건: 부하 생성기 `--hot-seller-share 0.5`.
- 볼 것: 파티션별 유입률과 lag, 키에 접미사를 붙여 흩었을 때 순서 보장이 깨지는 범위.
- 근거 등급: `E2`.

### E4-8. 브로커를 하나씩 재시작하면 클라이언트는 무엇을 볼까?

- 질문: 롤링 재시작 동안 프로듀서 오류, 재시도, 지연은 얼마나 늘까?
- 방법: 브로커를 한 대씩 멈추고, ISR이 복구된 것(UnderReplicatedPartitions 0)을 확인한 뒤 다음 브로커로 갑니다. 확인 없이 연달아 재시작하는 경우와 비교합니다.
- 볼 것: 프로듀서 오류 건수, 지연 p99, 단계별 UnderReplicatedPartitions.
- 근거 등급: `E2` (Kafka 문서의 롤링 업그레이드 절차).

### E4-9. 한 시간 멈췄다면 언제 따라잡을까?

- 질문: 유입 1만/s, 처리 1.2만/s일 때 1시간 정지 뒤 따라잡는 데 5시간(= 정지 시간 × 유입 / (처리 − 유입))이 걸린다는 계산은 실제와 맞을까?
- 축소: 노트북에서는 유입과 처리 속도를 낮추고 정지 시간을 10분으로 둡니다. 비율은 같게 유지합니다.
- 볼 것: 예측 시간과 실측 시간, 따라잡는 동안 처리량이 일정했는지.
- 근거 등급: `E2`.
