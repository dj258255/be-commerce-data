# 6장. 레이크하우스

## 이 장은 어디서 시작하나?

원본은 지금 상태만, 토픽은 하루치만 들고 있습니다. 정산 분쟁이 생기면 석 달 전 취소 이력을 다시 봐야 하고, 집계 규칙을 바꾸면 과거 전체를 다시 계산해야 합니다. CDC 토픽을 Iceberg 테이블에 적재해 이력을 싸게 오래 둡니다.

환경: `docker compose --profile cdc --profile lake up -d --wait`. Iceberg REST 카탈로그 Lakekeeper(`http://127.0.0.1:8181`, 창고 `lake`), S3 호환 저장소 SeaweedFS(`127.0.0.1:8333`), Trino(`http://127.0.0.1:8088`, 카탈로그 `lake`). 적재 작업은 5장 Flink 또는 Python(PyIceberg)으로 씁니다.

## 무엇을 공부하나?

- Iceberg 스냅샷, 매니페스트, 메타데이터 파일 (블로그 19편)
- 유지보수: 컴팩션, 스냅샷 만료, orphan 파일 정리 (블로그 20편)
- CDC를 MERGE로 반영하기, position delete와 equality delete (블로그 21편)
- 사실 테이블과 차원 테이블, 변경 이력(SCD Type 2)
- 브랜치와 write-audit-publish
- 파티션 진화

## 실험

### E6-1. CDC를 MERGE로 반영하면 읽기는 얼마나 느려질까?

- 질문: `payments`의 갱신과 취소를 MERGE로 반영할 때 삭제 파일이 쌓이면 조회 시간은 어떻게 변할까?
- 바꿀 조건: 쓰기 엔진(Flink는 equality delete, Trino MERGE는 position delete), 컴팩션 전후.
- 볼 것: 데이터 파일과 삭제 파일 수, 같은 조회의 시간, 원본과의 행 수·합계 비교.
- 판매자 테이블은 SCD Type 2로 만들어 변경 이력을 남깁니다.
- 근거 등급: `E2`.

### E6-2. 커밋을 자주 하면 파일은 몇 개가 될까?

- 질문: 적재 커밋 간격 10초, 60초, 5분에서 하루치 파일 수와 조회 시간은 얼마나 다를까?
- 볼 것: 파일 수, 평균 파일 크기, 조회 계획의 분할 수와 시간, 컴팩션에 걸린 시간.
- 근거 등급: `E2`.

### E6-3. 스냅샷을 지우면 무엇을 못 하게 될까?

- 질문: 스냅샷 만료 뒤 시간 여행 조회는 어디까지 될까? 진행 중인 쓰기가 있을 때 orphan 파일 정리를 짧은 기준으로 돌리면 무엇이 깨질까?
- 볼 것: 만료 전후 조회 가능 범위, 저장 용량, orphan 정리 뒤 테이블 상태.
- 근거 등급: `E2` (Iceberg 문서의 orphan 파일 삭제 경고, 기본 3일).

### E6-4. 두 테이블이 서로 다른 시점이면 조인 결과는?

- 질문: `payments`는 최신 커밋을, `settlement_items`는 한 커밋 전을 보고 있을 때 정산 대상 조인은 어떤 행을 잘못 낼까?
- 방법: 두 테이블을 따로 커밋하는 경우와, 브랜치에 쓰고 검사한 뒤 함께 공개하는 경우를 비교합니다.
- 볼 것: 어긋난 행 수, 공개 지연.
- 근거 등급: `E2`.

### E6-5. 날짜 파티션을 시간 파티션으로 바꾸면?

- 질문: 파티션 진화 뒤 옛 파일과 새 파일이 섞인 테이블의 조회는 어떻게 계획될까?
- 볼 것: 파티션 사양별 파일 분포, 조회 계획의 파일 제외 수.
- 근거 등급: `E2`.

## 이 장이 끝나면 남는 문제

이제 데이터는 원본, 토픽, 실시간 집계, 레이크, 배치 집계 다섯 곳에 있습니다. 숫자가 틀렸다는 연락이 오면 어느 구간에서 틀렸는지 찾아야 합니다. 7장으로 갑니다.
