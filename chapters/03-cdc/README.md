# 3장. CDC

## 이 장은 어디서 시작하나?

1장과 2장에서 분석 쿼리와 backfill이 결제 트랜잭션을 느리게 만들었습니다. 원본 DB에 묻는 대신, 원본이 이미 남기는 변경 기록(binlog)을 읽어 Kafka로 옮깁니다. 원본 부담은 줄지만 이제 원본과 사본이 같은지 따로 확인해야 합니다.

환경: `docker compose --profile cdc up -d --wait` 뒤 `scripts/register-connector.sh`. 토픽 이름은 `bcd.becommerce.<표>`입니다. MySQL은 ROW 형식, 전후 이미지 FULL, GTID 켬으로 떠 있습니다.

## 무엇을 공부하나?

- binlog: ROW 형식, 전후 이미지, GTID, 보존 기간(`binlog_expire_logs_seconds`, 기본 30일)
- Debezium MySQL 커넥터: 초기 스냅샷, 스트리밍 전환, 오프셋 토픽(`_connect_offsets`), 스키마 이력 토픽
- 레코드 모양: `op`(c, u, d, r), `before`, `after`, `source.ts_ms`, `source.gtid`
- CDC로 레이크하우스 채우기 (블로그 21편)

## 실험

### E3-1. 스냅샷을 뜨는 동안 들어온 변경은 빠질까?

- 질문: 데이터가 쌓인 뒤 커넥터를 등록하면 초기 스냅샷이 끝나기 전에 들어온 주문·취소는 어떻게 될까?
- 조건: 원본 10만 행 이상, 부하 생성기를 돌린 채 커넥터 등록.
- 볼 것: 원본 최종 상태와 토픽을 재생한 최종 상태의 행별 비교(빠진 행, 값이 다른 행), 스냅샷 소요 시간, 그동안의 주문 트랜잭션 지연.
- 근거 등급: `E2`.

### E3-2. 커넥터가 죽었다 살아나면 같은 변경이 두 번 올까?

- 질문: Connect 컨테이너를 `kill -9`로 죽이고 다시 띄우면 중복 레코드는 몇 건 생길까?
- 바꿀 조건: `offset.flush.interval.ms` 기본값(60초)과 5초.
- 볼 것: (GTID, 표, 키, op) 기준 중복 건수, 중복이 생긴 시간 범위.
- 근거 등급: `E2`.

### E3-3. binlog가 먼저 지워지면?

- 질문: 커넥터가 멈춘 사이 binlog 보존 기간이 지나면 재시작한 커넥터는 무엇을 할까?
- 조건: `binlog_expire_logs_seconds`를 짧게 줄이고, 커넥터를 멈춘 채 쓰기를 계속하고 `FLUSH BINARY LOGS`.
- 볼 것: 커넥터 상태와 오류, 복구 절차(오프셋 삭제와 재스냅샷 또는 `snapshot.mode` 변경), 복구에 걸린 시간과 다시 읽은 행 수.
- 근거 등급: `E2`.

### E3-4. 스트리밍 중에 컬럼이 추가되면?

- 질문: `ALTER TABLE payments ADD COLUMN ...`이 흐르는 동안 CDC 레코드와 스키마 이력 토픽은 어떻게 바뀔까?
- 볼 것: 변경 전후 레코드 모양, 스키마 이력 토픽 내용, 소비자가 깨지는 경우.
- 7장 E7-4(의미가 바뀌는 스키마 변경)와 짝입니다.
- 근거 등급: `E2`.

## PostgreSQL이었다면?

BE-commerce가 MySQL이라 이 장은 binlog를 다룹니다. PostgreSQL에서는 복제 슬롯이 소비자가 읽은 위치를 원본에 붙잡아 두기 때문에, 소비자가 멈추면 binlog처럼 지워지는 대신 WAL이 원본 디스크에 쌓입니다. `max_slot_wal_keep_size`(기본 -1, 무제한)로 상한을 두면 디스크는 지키지만 슬롯을 잃습니다. 두 방식의 차이를 E3-3 결과와 함께 표로 정리합니다.

## 이 장이 끝나면 남는 문제

이제 모든 변경이 Kafka를 지납니다. 브로커 하나가 죽거나 소비자가 재시작될 때 무엇을 잃고 무엇이 두 번 오는지 알아야 합니다. 4장으로 갑니다.

## 블로그 글 후보

- 커넥터가 RUNNING인데 데이터가 안 오는 경우(E3-3)
- CDC 커넥터 재시작과 중복(E3-2)
