# 1장. 하루 매출 숫자

## 이 장은 어디서 시작하나?

BE-commerce가 돌기 시작하면 첫 요청은 대개 "어제 판매자별 매출을 뽑아 주세요"입니다. 분석용 저장소는 아직 없으니 운영 MySQL에 SQL을 직접 던집니다. 이 장은 그 SQL 한 줄이 생각보다 많은 결정을 숨기고 있다는 데서 시작합니다. 어떤 행을 세는지, 취소를 언제 빼는지, 어제가 몇 시부터 몇 시까지인지 정하지 않으면 같은 표에서 서로 다른 숫자가 나옵니다.

환경: `docker compose up -d --wait` (MySQL만). 데이터는 `loadgen/loadgen.py`.

## 무엇을 공부하나?

- grain: `orders`는 주문 하나, `order_items`는 주문 안의 상품 한 줄, `payment_history`는 상태 전이 한 번, `internal_records`는 승인 또는 취소 한 번이 한 행입니다.
- 조인 카디널리티: 1:N 조인 뒤에 1쪽 금액을 합치면 N배가 됩니다.
- 매출의 정의: 승인 금액(`internal_records.seq = 0`), 취소 반영 금액(모든 seq 합), 현재 잔액(`payments.balance_amount`)은 취소가 다른 날 일어나면 서로 다른 값이 됩니다.
- 시간대: 원본의 시각 열은 UTC이고 영업일 `trade_date`는 KST 날짜입니다(BE-commerce V21 규칙).
- 실행 계획: MySQL 8.4 `EXPLAIN ANALYZE`.

## 실험

### E1-1. 조인 한 번에 매출이 얼마나 부풀까?

- 질문: `orders`에 `order_items`와 `payment_history`를 붙인 뒤 `SUM(orders.total_amount)`을 하면 정답과 얼마나 다를까?
- 가설: 주문당 상품 줄 수 × 상태 전이 수만큼 배수가 됩니다. 부하 생성기 기본값에서 상품 줄은 평균 2, 전이는 2~3이라 4~6배 근처일 것입니다.
- 정답: `internal_records`의 seq 0 합계.
- 볼 것: 오차율, 주문당 행 수 분포, `COUNT(DISTINCT)`나 사전 집계로 고친 쿼리의 결과와 실행 시간.
- 근거 등급: `E2`.

### E1-2. 어제는 몇 시부터 몇 시까지일까?

- 질문: `DATE(recorded_at)`(UTC)로 자른 하루 매출과 `trade_date`(KST)로 자른 하루 매출은 얼마나 다를까?
- 조건: 부하 생성기를 UTC 0시 전후로 돌리거나, `recorded_at`을 옮겨 하루치 분포를 만듭니다.
- 볼 것: 두 기준의 날짜별 건수와 금액 차이. 차이는 KST 0시~9시 구간에 몰려야 합니다.
- 근거 등급: `E2`.

### E1-3. 취소는 언제의 매출에서 빼야 할까?

- 질문: 어제 승인되고 오늘 취소된 결제는 어제 매출일까, 오늘 매출일까?
- 볼 것: 승인일 기준, 취소일 기준, 현재 잔액 기준 세 정의의 날짜별 값과 차이. 어제 숫자가 오늘 다시 뽑으면 바뀌는지.
- 이 실험이 2장의 잠정치와 확정치로 이어집니다.
- 근거 등급: `E2`.

### E1-4. 분석 쿼리가 결제 쓰기를 느리게 할까?

- 질문: E1-1의 큰 집계 쿼리가 도는 동안 부하 생성기의 주문 트랜잭션 지연은 얼마나 늘까?
- 준비: 부하 생성기에 트랜잭션별 지연 기록을 추가합니다(열린 루프로 바꿔야 coordinated omission을 피합니다).
- 바꿀 조건: 분석 쿼리 동시 실행 수 0, 1, 4.
- 고정할 조건: 주문률, 데이터 양, 버퍼 풀 크기.
- 볼 것: 주문 트랜잭션 p50, p95, p99, 쿼리가 읽은 행 수, 버퍼 풀 히트율.
- 이 결과가 3장에서 CDC를 들이는 이유가 됩니다.
- 근거 등급: `E2`.

## 이 장이 끝나면 남는 문제

쿼리를 고쳐 맞는 숫자를 얻어도 매일 아침 누군가 돌려야 합니다. 돌리다 실패하면 다시 돌려야 하고, 다시 돌리면 숫자가 두 번 들어갈 수 있습니다. 2장으로 갑니다.
