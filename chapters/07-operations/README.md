# 7장. 운영과 대조

## 이 장은 어디서 시작하나?

파이프라인이 원본에서 토픽, 실시간 집계, 레이크, 배치 집계까지 길어졌습니다. 서버가 살아 있는지는 헬스체크가 알려 주지만, 데이터가 제때 빠짐없이 맞게 왔는지는 아무도 알려 주지 않습니다. 이 장은 그 질문에 답하는 장치를 만들고, 일부러 틀린 데이터를 넣어 장치가 잡는지 확인합니다.

환경: 실험마다 앞 장의 프로필을 조합합니다. 대조 도구는 원본(MySQL), 토픽(Kafka), 레이크(Trino)를 모두 읽습니다.

## 무엇을 공부하나?

- 데이터 품질의 세 축: 신선도, 완전성, 정확성
- 대조: 건수, 합계, 키 범위별 해시
- 종단 지연을 구간별로 나누기, 백분위와 측정 함정 (블로그 9편, 10편)
- Kafka Connect 오류 처리(`errors.tolerance`, DLQ 토픽)와 재처리
- 스키마 호환성 검사가 잡지 못하는 의미 변경 (블로그 15편)
- 펜싱: 오래된 작업의 쓰기를 막는 세대 번호

## 실험

### E7-1. 작업은 성공했는데 행이 빠졌다면 어떻게 찾을까?

- 질문: 원본, 토픽, 레이크를 3층으로 대조하면 일부러 빠뜨린 행을 어느 층에서 어느 키까지 짚을 수 있을까?
- 장애 주입: 적재 작업이 일부 오프셋을 건너뛰게 하거나, 레이크에서 행을 지웁니다.
- 대조 3층: 1층 건수와 합계, 2층 키 범위 청크 해시, 3층 어긋난 청크의 행 단위 비교.
- 볼 것: 각 층이 잡은 것과 비용(읽은 행 수, 시간), 거짓 불일치(재스냅샷이 섞였을 때 등).
- 근거 등급: `E1·축소` (Uber 원장 이관의 오프라인 전수 비교를 축소).

### E7-2. 원본 커밋에서 조회까지 어느 구간이 늦을까?

- 질문: 원본 커밋 → binlog 기록(`source.ts_ms`) → Kafka 기록(레코드 타임스탬프) → Flink 처리 → Iceberg 커밋 → 조회 가능까지 구간별 지연은 얼마일까?
- 만들 것: 구간별 지연 히스토그램, 신선도 SLO(예: p99 5분) 정의와 경보 조건.
- 볼 것: 구간별 p50, p95, p99, 가장 긴 구간, 부하를 올렸을 때 먼저 늘어나는 구간.
- 근거 등급: `E2`.

### E7-3. DLQ에서 고쳐 다시 넣었더니 최신 값을 덮었다면?

- 질문: 변환 오류로 DLQ에 간 결제 갱신을 나중에 고쳐 재투입하면, 그사이 들어온 더 새로운 갱신을 덮어쓰지 않을까?
- 방법: 커넥터나 소비자 단계에서 오류를 내 DLQ로 보내고, 같은 결제의 후속 갱신이 먼저 반영된 뒤 재투입합니다.
- 볼 것: 덮어쓴 건수, `version` 비교(BE-commerce의 낙관적 락 버전)로 막았을 때의 결과, DLQ 미처리 건수를 지표로 내는 방법.
- 근거 등급: `E2`.

### E7-4. 적재는 성공했는데 지표가 틀렸다면?

- 질문: 금액 단위를 원에서 전으로 바꾸거나 `recorded_at`을 KST로 쓰기 시작하면 스키마 호환성 검사는 통과하고 지표만 틀립니다. 무엇으로 잡을까?
- 만들 것: 분포 검사(합계와 중앙값의 전날 대비 비율), 데이터 계약(열 단위·시간대 명시).
- 볼 것: 호환성 검사 결과, 분포 검사가 잡기까지 걸린 시간, 놓친 경우.
- 근거 등급: `E2`.

### E7-5. 지운 판매자가 다시 나타날까?

- 질문: 판매자 탈퇴로 원본에서 행을 지운 뒤, 토픽 재생이나 이전 스냅샷 복구를 하면 그 판매자가 레이크와 집계에 다시 나타날까?
- 볼 것: 경로별(토픽 재생, Iceberg 시간 여행 복구, MySQL 백업 복구) 되살아난 행 수, 삭제 기록(tombstone, 삭제 대장)으로 막았을 때의 결과.
- 근거 등급: `E2`.

### E7-6. 멈춘 줄 알았던 이전 작업이 늦게 쓰면?

- 질문: 재시작한 집계 작업이 결과를 쓴 뒤, 멈춘 줄 알았던 이전 작업이 늦게 깨어나 옛 결과를 쓰면 무엇이 남을까?
- 방법: 이전 작업을 `SIGSTOP`으로 멈췄다가 새 작업이 끝난 뒤 `SIGCONT`.
- 볼 것: 최종 결과, 세대 번호를 쓰기 조건에 넣었을 때 거부된 쓰기 수.
- 근거 등급: `E2`.

### E7-7. 서버 운영 항목을 데이터 운영 항목으로 바꾸면?

서버 운영에서 흔히 챙기는 아홉 가지(자동 재시작, 헬스체크와 알림, 지연 측정, DLQ, 무중단 배포, 버전 관리, 백업, 분산, 로깅)를 이 시스템 기준으로 표로 만듭니다. 칸마다 "서버 관점에서 보는 것", "데이터 관점에서 더 봐야 하는 것", "이 저장소에서 확인한 실험"을 채웁니다. 예를 들어 자동 재시작은 서버 관점에서 프로세스 복구지만, 데이터 관점에서는 재시작 뒤 중복(E3-2, E4-3)과 lag 소진(E4-9)까지 봐야 합니다.

## 이 장이 끝나면 남는 문제

틀린 곳을 찾을 수 있게 됐지만, 고칠 때마다 과거 전체를 다시 계산하면 비용이 큽니다. 8장으로 갑니다.

## 블로그 글 후보

- 원본과 목적지를 3층으로 대조하기(E7-1)
- 신선도 SLO를 구간별로 나누기(E7-2)
- DLQ 재투입이 최신 값을 덮는 경우(E7-3)
