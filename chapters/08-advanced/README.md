# 8장. 고난도

## 이 장은 어디서 시작하나?

7장에서 틀린 곳을 찾게 됐습니다. 이제 문제는 고치는 비용입니다. 늦은 취소 하나 때문에 한 달치를 다시 계산하거나, 집계 로직을 바꿀 때마다 토픽 전체를 다시 읽으면 규모가 커질수록 감당하기 어렵습니다. 이 장의 실험은 앞 장의 결과가 모두 있어야 할 수 있습니다.

## 실험

### E8-1. 늦은 변경이 닿은 날짜만 다시 계산할 수 있을까?

- 질문: 지난 30일 중 늦은 취소가 들어온 날짜만 골라 다시 계산하면 전체 재계산과 같은 결과를 더 싸게 낼 수 있을까?
- 방법: 레이크의 변경 이력(Iceberg 증분 읽기)에서 영향받은 `trade_date`를 뽑고 그 파티션만 다시 씁니다.
- 볼 것: 재계산한 파티션 수, 소요 시간, 전체 재계산과의 결과 차이(0이면 비교가 실제로 돌았다는 증거 함께).
- 참고 사례: Netflix Psyberg(2023). 원문을 직접 열지 못해 미러로만 확인했으므로 수치는 인용하지 않습니다.
- 근거 등급: `E1·축소`.

### E8-2. 처음부터 다시 돌린 결과가 실시간 결과와 같을까?

- 질문: 5장 실시간 집계를 토픽 처음부터 재생해 다시 계산하면 실시간으로 낸 결과와 같은 값이 나올까? 다르면 무엇 때문일까?
- 볼 것: 판매자·윈도별 차이, 원인 분류(처리 시간 의존, watermark, 외부 조회, 비결정적 함수).
- 참고 사례: Uber의 Kappa 아키텍처 재처리 글(2020).
- 근거 등급: `E1·축소`.

### E8-3. 작업 수백 개가 한꺼번에 다시 돌면?

- 질문: Airflow에서 판매자별 작업 수백 개를 동시에 backfill하면 스케줄러가 작업을 띄우는 지연은 얼마나 늘까?
- 바꿀 조건: 작업 수 50, 200, 500, 풀 크기.
- 볼 것: 예정 시각과 실제 시작 시각의 차이 분포, 스케줄러 루프 시간, 메타 DB 부하.
- 근거 등급: `E2`.
