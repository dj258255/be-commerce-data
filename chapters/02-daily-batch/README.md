# 2장. 매일 돌리는 집계

## 이 장은 어디서 시작하나?

1장에서 맞는 SQL을 얻었습니다. 이제 매일 아침 그 SQL로 `daily_seller_revenue` 표를 채우는 작업을 만듭니다. 한 번 돌릴 때는 문제가 없던 SQL이, 실패와 재실행과 지난 날짜 다시 돌리기를 만나면 다른 숫자를 냅니다.

환경: `docker compose --profile orchestrate up -d`. Airflow 3 standalone(`http://127.0.0.1:8080`, 계정은 컨테이너의 `/opt/airflow/simple_auth_manager_passwords.json.generated`). DAG는 `airflow/dags/`에 둡니다. 원본 연결 이름은 `becommerce`입니다.

## 무엇을 공부하나?

- 오케스트레이터가 맡는 일: 스케줄, 의존, 재시도, 상태 기록 (블로그 3편)
- 멱등성과 재시도·백오프 (블로그 4편)
- 논리 날짜와 backfill (블로그 5편)
- 동시성 제한 (블로그 7편)
- 멱등 쓰기 방법: 날짜 파티션 지우고 다시 쓰기, `INSERT ... ON DUPLICATE KEY UPDATE`
- 잠정치와 확정치: 늦게 확정되는 데이터가 있을 때 숫자를 언제 닫을지

## 실험

### E2-1. 다시 돌리면 매출이 두 배가 될까?

- 질문: 같은 날짜를 두 번 돌리면 `INSERT`만 하는 작업과 날짜 단위로 덮어쓰는 작업의 결과는 어떻게 다를까?
- 장애 주입: 쓰기 도중 작업을 죽이고 재시도가 다시 돌게 합니다.
- 볼 것: 재실행 뒤 합계와 정답의 차이, 부분 쓰기가 남는지.
- 근거 등급: `E2` (Airflow 문서의 작업 설계 권고: 재실행해도 같은 결과, INSERT 대신 UPSERT).

### E2-2. 늦게 확정되는 결제는 어제 숫자를 바꿀까?

- 질문: KST 23시 59분에 응답을 모르게 된(`UNKNOWN`) 결제가 0시 5분에 복구 배치로 `DONE`이 되면 어제 매출은 언제 확정할 수 있을까?
- 조건: 부하 생성기 `--unknown-rate`를 올리고 0시 경계를 넘깁니다.
- 볼 것: 아침 작업 시점의 잠정치와 하루 뒤 확정치의 차이, 다시 집계해야 하는 날짜 수, 차이가 0이 되는 데 걸리는 시간.
- 근거 등급: `E2`.

### E2-3. 30일 backfill을 한꺼번에 돌려도 될까?

- 질문: 30일치를 동시에 다시 돌리면 원본 DB의 결제 쓰기는 얼마나 느려질까?
- 바꿀 조건: 동시 실행 수(`max_active_runs`) 1, 4, 8.
- 볼 것: 총 소요 시간, 부하 생성기의 주문 트랜잭션 p95, MySQL 활성 연결 수.
- 이 결과도 3장 CDC의 이유가 됩니다.
- 근거 등급: `E2`.

### E2-4. 작업이 성공했는데 0행이면?

- 질문: 날짜 조건 실수로 0행을 쓴 작업은 성공으로 끝납니다. 무엇으로 잡을까?
- 만들 것: 건수 하한 검사, 전날 대비 변화율 검사, 신선도 검사(마지막 원본 행 시각).
- 볼 것: 검사가 잡은 경우와 놓친 경우. 0이 나오면 검사가 실제로 돌았다는 증거를 함께 남깁니다.
- 근거 등급: `E2`.

## 이 장이 끝나면 남는 문제

E1-4와 E2-3에서 분석 작업이 원본 DB를 짓누릅니다. 원본에서 직접 읽는 방식을 바꿔야 합니다. 3장으로 갑니다.
